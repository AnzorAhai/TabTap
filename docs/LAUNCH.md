# Перед запуском с настоящими ресторанами

Техническая часть фазы 6 сделана. Ниже — что осталось, и всё это требует ваших решений, аккаунтов или
внешних людей. Для инвесторского показа ничего из этого не обязательно, кроме смены пароля.

## Что уже работает

- **Изоляция ресторанов в базе.** Запросы персонала выполняются от ограниченной роли `tabtap_app` с
  row-level security: ошибка в коде не откроет данные другого ресторана. Гостевые страницы, фоновые задачи
  и раздел платформы работают между ресторанами и используют обычное подключение. Нужен session pooler
  Supabase (порт 5432): с transaction pooler (6543) API откажется запускаться.
- **Отчёты об ошибках.** Подключены к Sentry, включаются переменной `SENTRY_DSN`. В отчёт уходит только
  ошибка и стек, без адресов, заголовков и данных гостей.
- **Резервные копии.** Ночная зашифрованная копия базы через GitHub Actions, включается двумя секретами.
- **Нагрузочный тест** (`npm run test:load`, только локально). На компьютере разработчика с базой рядом:
  около 1 800 чтений счёта в секунду при 50 одновременных запросах (p95 — 33 мс), экран персонала p95 —
  24 мс. Когда 30 гостей одновременно платят за одно и то же, платёж проходит один раз, суммы сходятся, ошибок
  сервера нет. Серверы Render заметно слабее, база там дальше: эти цифры — проверка логики, а не прогноз.

## Сделать до первого настоящего ресторана

1. **Сменить пароль `admin`** на длинный:
   `npm run users:invite -- --login admin --password "длинный пароль"`.
2. **Подключить Sentry.** Создать бесплатный проект Node на sentry.io, скопировать DSN, добавить на Render
   переменную `SENTRY_DSN`. Sentry сам присылает письмо о новой ошибке.
3. **Включить резервные копии.** На GitHub: Settings → Secrets and variables → Actions, добавить
   `BACKUP_DATABASE_URL` (строка подключения Supabase) и `BACKUP_PASSPHRASE` (длинная фраза, хранить отдельно:
   без неё копию не восстановить). Затем Actions → Database backup → Run workflow и убедиться, что появился
   файл. Копии хранятся 30 дней. Этот запуск ещё ни разу не проверялся на настоящей базе.
4. **Один раз проверить восстановление** в пустую базу:
   ```bash
   gpg --decrypt tabtap.dump.gpg | pg_restore --no-owner --no-privileges --dbname "$NEW_DATABASE_URL"
   ```
   Альтернатива — платный план Supabase с ежедневными копиями.
5. **Перевыпустить Deploy Hook** в Render (Settings → Deploy Hook): его ключ однажды попал в вывод инструмента.
6. **Переехать ближе к Венесуэле**: сервер и база в US East, порядок действий — в README, раздел Region.
7. **Платный план Render.** На бесплатном сервер засыпает, а гость не будет ждать минуту.
8. **Выключить демо**: подключить настоящую кассу и платёжный шлюз вместо `POS_CONNECTOR_TYPE=demo` и
   `PAYMENT_PROVIDER_TYPE=mock`, перевести проверку переводов с «Демо» на сотрудника.

## Тестовый стенд

Понадобится, когда появятся настоящие деньги: копия всего, где можно пробовать без риска. Это отдельный проект
Supabase, отдельный сервис Render и две новые среды Vercel со своими `VITE_API_URL` и `CORS_ORIGINS`.

## Вопросы юристу и бухгалтеру

Это не юридическое заключение, а список того, что нужно выяснить до приёма денег:

- **Санкции США.** Можно ли работать с венесуэльскими ресторанами и банками, в том числе с государственными,
  через американские сервисы: Render, Vercel, Supabase, GitHub, Sentry. Что с Zelle и Binance.
- **Фискальные документы SENIAT.** Кто выдаёт фискальный документ: касса ресторана или TabTap. Сейчас чек
  TabTap помечен как не фискальный.
- **IGTF.** Кто обязан его взимать и когда, включать ли надбавку по умолчанию.
- **Модель денег и комиссии.** Гость платит напрямую ресторану, TabTap выставляет ему счёт за комиссию раз в
  месяц. Нужны договор с рестораном и подтверждение, что это не требует лицензии.
- **Персональные данные гостей**: телефоны и имена из подтверждений переводов.
