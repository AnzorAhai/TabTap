# TabTap — план до демо и запуска

Документ фиксирует принятые решения и порядок работ. Обновляется по мере продвижения.

## Принятые решения

| Вопрос                   | Решение                                                                                         |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| Рынок                    | Южная Америка, позже, возможно, Африка. **Первая страна и страна демо — Венесуэла.**            |
| Валюта                   | Счёт в USD; оплата в USD или в боливарах (VES) по курсу BCV, зафиксированному на момент оплаты. |
| Способы оплаты           | Pago Móvil (VES), Zelle, Binance/USDT, наличные официанту, карта через терминал.                |
| Языки                    | Испанский — основной; английский и русский — переключатель для показа инвестору.                |
| Способы разделения счёта | Первая версия: весь счёт, свои блюда, поровну.                                                  |
| Комиссия платформы       | 1.5%, платит ресторан.                                                                          |
| Авторизация              | Своя, в API (без Supabase Auth) — хостинг может смениться.                                      |
| Интерфейс                | Сразу в коде, без отдельного этапа макетов.                                                     |
| Касса для демо           | Своя демо-касса (экран официанта); интеграции с реальной кассой пока нет.                       |
| Хостинг                  | Render (API) + Vercel (фронты) + Supabase (БД); переезд на восток США — отдельный шаг.          |

## Фазы

### Фаза 0. Фундамент — сделано

- Зависимости на актуальных версиях: NestJS 12, React 19, Vite 8, TypeScript 6. Уязвимостей в
  продакшен-зависимостях нет.
- ESLint (с правилами, учитывающими типы), Prettier, Vitest, GitHub Actions: формат, линт, типы,
  тесты, сборка и проверка миграций на чистом Postgres.
- API: проверка конфигурации при старте, `/health` с проверкой БД, логи запросов (JSON в
  продакшене), единый формат ошибок без утечки деталей, проверка UUID и тела запросов, helmet,
  CORS только для своих доменов, ограничение частоты запросов, корректное завершение.
- Миграции применяются при каждом старте API (с блокировкой от параллельного запуска).
- Конфиги деплоя в репозитории: `render.yaml`, `vercel.json`; переезд в US East описан в README.
- README и `.env.example` для всех приложений.

### Фаза 1. Ядро: счета, разделение, платежи — сделано

- Уникальные ограничения и индексы, атомарное сохранение счёта — без дублей при одновременном скане.
- Сервер сам считает сумму: клиент сообщает только, что оплачивает (весь остаток, свои блюда, N
  долей); сумма, чаевые, комиссия и сумма в валюте оплаты — на сервере.
- Единый остаток счёта для всех способов — переплата невозможна, запросы к одному счёту идут строго
  по очереди. Деление поровну общее для стола; суммы долей фиксируются при первой оплате доли.
- Начатый платёж резервирует блюда/доли на `PAYMENT_HOLD_MINUTES` (10 мин); при отказе, отмене или
  истечении резерв снимается. Деньги, пришедшие после истечения резерва, всё равно записываются.
- Две валюты: счёт в USD, оплата в USD или VES по курсу ресторана; платёж хранит использованный курс.
  Курс задаётся через `POST /admin/exchange-rates` (временный токен администратора до фазы 2).
- Разбивка как на бумажном счёте: подытог, IVA, сервис, итого; цена строки включает её налог и долю
  сервиса, сумма строк ровно равна итогу.
- Жизненный цикл платежа: запись в БД → провайдер → подтверждение (вебхук, запасной путь — запрос
  статуса) → проведение, чек и уведомление кассы в одной транзакции; ключ идемпотентности против
  двойного списания.
- Уведомления кассы через очередь с повторами (касса недоступна — данные не теряются).
- Комиссия 1.5% (настройка ресторана) сохраняется по каждому платежу, без учёта чаевых.
- Все гости за столом видят изменения сразу (SSE; запасной путь — опрос).
- Демо-ресторан переведён на Венесуэлу: меню в USD, IVA 16%, сервис 10%, демо-курс 236.5 VES.
- Гостевое приложение и админка переведены на новое API (функционально; дизайн — фаза 4).
- `npm run db:local` — настоящий PostgreSQL для разработки без Docker; на нём же идут тесты.
- Тесты: 16 модульных (деньги, разбивка счёта) и 22 интеграционных на реальном Postgres (гонки,
  идемпотентность, резервы, деление, валюта, очередь кассы).

### Фаза 2. Рестораны и доступ к админке — сделано

- Вход для персонала по логину и паролю (scrypt), сессии с ограниченным сроком, выход, немедленная
  потеря доступа при отключении аккаунта или снятии роли.
- Роли в ресторане: владелец (всё, включая сотрудников), менеджер (столы, курс, настройки,
  официанты), официант (просмотр). Администратор платформы видит все рестораны как владелец.
- Приглашения одноразовыми ссылками (72 ч) вместо писем: пригласивший отправляет ссылку сам,
  приглашённый задаёт пароль. Первый аккаунт — командой `npm run users:invite`.
- Все данные админки — только по ресторану из сессии; чужие рестораны и их столы недоступны.
- Случайные QR-токены столов (128 бит) вместо `table-1`; перевыпуск QR в один клик.
- Управление: столы (создание, переименование, отключение, ID в кассе), курс, валюты оплаты,
  варианты чаевых, название ресторана, сотрудники.
- Платформа: подключение ресторана вместе с владельцем, комиссия (только платформа), приостановка
  ресторана, ссылка для сброса пароля.
- Служебные таблицы закрыты от публичного REST API Supabase (RLS).
- Корректная остановка API при деплое: новые запросы получают 503, SSE-потоки закрываются,
  незавершённые запросы к базе дожидаются окончания.
- Админка: вход, установка пароля по ссылке, выбор ресторана, разделы управления; CSP-заголовок.

### Фаза 3. Способы оплаты Венесуэлы — сделано (симулятор; реальные банки — позже)

- Способы оплаты на ресторан: Pago Móvil (Bs), Zelle (USD), Binance Pay (USDT ≈ USD), наличные USD и
  Bs официанту, карта через шлюз. Деньги идут напрямую ресторану.
- Реквизиты для гостя (банк, телефон, RIF, email Zelle, Binance Pay ID) с проверкой формата; гость
  видит точную сумму и реквизиты, затем сообщает номер операции.
- Подтверждение: персонал в админке («Деньги получены» / «Отклонить», официанты тоже — для
  наличных) или демо-симулятор банка для Pago Móvil (номер, оканчивающийся на 0000, «не найден»).
- Надбавки по способу оплаты (например, IGTF 3% на валюту вне банковской системы) — настраиваются
  рестораном; применимость IGTF зависит от статуса contribuyente especial, уточнять с бухгалтером.
- Резерв для оплат вне шлюза — 30 минут (гость платит в другом приложении или ждёт официанта).
- Курс BCV: автоматически каждый час из DolarAPI (`ve.dolarapi.com`) для ресторанов с источником
  «BCV», по кнопке или вручную; устаревшие и некорректные данные отбрасываются.
- Комиссия: отчёт по месяцам для ресторана и для платформы — основа ежемесячного счёта ресторану.
- Реальные подключения (API банков для проверки Pago Móvil, Binance Pay merchant API) — когда
  появится банк-партнёр или пилотный ресторан.

### Фаза 4. Интерфейс — сделано

- Гостевое приложение: заведение и стол → счёт → способ (весь / свои блюда / поровну) → чаевые и
  способ оплаты → оплата → успех и чек; чек отправляется в WhatsApp. Кнопка «назад» телефона
  проходит по шагам. Начатый платёж переживает перезагрузку вкладки (гость уходит в приложение
  банка и возвращается).
- Настоящий PWA: установка на телефон, иконки, приложение открывается без сети и само загружает
  счёт, когда связь вернулась. Вес гостевого приложения — 85 КБ JS (gzip), без веб-шрифтов.
- Языки: испанский (по умолчанию), английский, русский — в гостевом приложении и админке.
  Тёмная тема — по настройке телефона.
- Админка: «Сегодня» (ждут подтверждения, сводка за день, живой статус столов), платежи с фильтрами
  и выгрузкой CSV, возвраты, печать карточек столов с QR (4 на лист A4, на выбранном языке).
- Возврат: только владелец и менеджер. Возвращённый платёж не считается в продажах и комиссии, а
  то, что он оплачивал, снова к оплате (если касса не закрыла счёт). Кассу возврат не уведомляет —
  сторно на кассе остаётся за рестораном.

### Фаза 5. Демо-касса для инвестора — сделано (день показа — см. docs/DEMO.md)

- Демо-касса в БД и экран официанта в админке: открыть стол, добавить блюда из меню, закрыть стол.
  Каждое нажатие — отдельная порция, чтобы гости могли оплатить каждый своё.
- Сценарий: официант пробивает заказ → инвестор сканирует QR, делит счёт и платит → касса и
  админка за пару секунд показывают «оплачено» и чаевые.
- Демо-ресторан в Каракасе (El Araguaney), меню в USD с суммой в боливарах; кнопка «сбросить демо»
  работает только для ресторана с пометкой демо.
- День показа — решения владельца: API не засыпает (платный план Render на месяц или открытый экран
  кассы), свой домен, таблички с QR. Сценарий и чек-лист: [DEMO.md](DEMO.md).

### Фаза 6. Перед реальным запуском

- Изоляция данных ресторанов на уровне БД (RLS с отдельной ролью).
- Мониторинг ошибок, бэкапы, отдельный тестовый стенд, нагрузочный тест.
- Требования Венесуэлы (цифровая фактура SENIAT — обычно на стороне кассы), проверка юристом по
  санкциям США.
- Реальные банковские интеграции и касса; переезд на серверы ближе к стране запуска.

## Открытые вопросы

- **Модель комиссии.** Реализовано так: гость платит напрямую ресторану, TabTap считает 1.5% с
  суммы счёта по каждой оплате, отчёт за месяц — основа счёта ресторану. Нужно подтверждение.
- **IGTF.** Включать ли надбавку 3% по умолчанию — зависит от статуса ресторана; уточнить у бухгалтера.
